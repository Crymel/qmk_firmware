# Crymel's QMK keymaps

## Keyboards & status

- **ErgoDox EZ** (`keyboards/ergodox_ez/keymaps/Crymel`) — main, daily-use keyboard. This is where all active tuning happens; treat it as the source of truth.
- **Redox wireless** (`keyboards/redox/wireless/keymaps/Crymel`) — secondary keyboard, currently frozen at a much older state (see log below). Not touched during ErgoDox tuning sessions. May get brought up to parity with the ErgoDox keymap later — when that happens, port forward from the ErgoDox keymap's *current* state, not from any memory of what Redox used to have.

## Working preferences

- One commit per logical change, or per explicit "commit this" (sometimes bundling several small related requests into one commit when the user says so). Never amend. Never push without an explicit, separate instruction to push, even right after a commit.
- Run `qmk compile -kb ergodox_ez -km Crymel` after every edit before considering it done.
- Clangd/editor diagnostics on `keymap.c` (`SAFE_RANGE` undeclared, `LAYOUT_ergodox_pretty` implicit declaration, etc.) are pre-existing and harmless — the editor's compile context is missing QMK's generated build headers. Unrelated to the real `avr-gcc` build; ignore them.
- `LAYOUT_ergodox_pretty(...)` takes 76 positional args in one call; eyeballing "which key is physically where" from the raw arg list is error-prone and has caused mistakes before. Use `keyboards/ergodox_ez/info.json` → `layouts.LAYOUT_ergodox_pretty.layout[i].matrix` / `.x` / `.y` (a quick Python script) to resolve spatial requests ("key above X", "left of Y") into exact argument indices before editing.
- `lib/lufa` showing as untracked in `git status` is a submodule/build dependency, not stray work — leave it alone.

## QMK mechanics worth remembering

These took real investigation into QMK core (`quantum/action_tapping.c`) to pin down — not obvious from the keymap file alone.

- **Layer resolution is highest-numbered-layer-wins**, scanned top-down for the first non-`KC_TRANSPARENT` keycode at a given matrix position. A default layer with no transparent keys (e.g. `_GAMING`) must be numbered *below* every overlay it needs to support (`_SYMB`, `_MOVE`, `_MOUSE`, `_SHORTCUTSMAC`, ...), or those overlays silently never show through even while their LED/toggle state is correctly active. Bit us once (see 2026-07-25/26 below) — both default layers now sit at the bottom (`_QWERTY`=0, `_GAMING`=1), everything else above.
- **Chordal Hold** (`chordal_hold_layout`) is keyed by the *physical matrix position of the hold key itself*, not by keycode or active layer. `'*'` = wildcard hand: that key always gets an instant hold decision on any interrupt, same-hand or not. `'L'`/`'R'` = the interrupting key must be on the *other* hand for an instant decision; a same-hand interrupt instead forces the held key to resolve as a **tap**, protecting ordinary same-hand rolling typing from accidental modifier activation. Thumb-row keys (Enter, Space) are `'*'` by convention for this reason; Backspace's hold silently misbehaved on same-hand chords until it was marked `'*'` too (2026-07-28).
- **Speculative Hold only applies to `MT()` mod-tap keys**, never to `LT()` layer-tap keys (`IS_QK_MOD_TAP` gate in `action_tapping.c`) — it does nothing for `LT(_SYMB, KC_ENT)`. It also only speculates Ctrl/Shift-only mod combos by default (`get_speculative_hold`'s default excludes Alt/Gui) — relevant if a future hold ever needs Alt or Gui speculated.
- **Without `HOLD_ON_OTHER_KEY_PRESS`, a tap-hold key's hold only commits when the *interrupting* key is released**, not when it's pressed — Permissive Hold's actual trigger point is the release event. So holding Enter/Backspace and pressing a symbol key sent nothing until that symbol key came back up. This, not `TAPPING_TERM`, was the real cause of "hold layers feel slow." Fixed narrowly for `LT(_SYMB, KC_ENT)`, `LCTL_T(KC_BSPC)`, `RCTL_T(KC_BSPC)` via `HOLD_ON_OTHER_KEY_PRESS_PER_KEY` + `get_hold_on_other_key_press()` (2026-07-28) — deliberately scoped rather than global, so home-row mods keep the more cautious default.
- **Flow Tap** (`get_flow_tap_term`) only ever fires when the *currently-resolving* key's tap output is in `is_flow_tap_key()`'s default set (`KC_A`–`KC_Z`, space, `.`, `,`, `;`, `/`). In this keymap that limits its effect entirely to the home-row mod-taps (A, S, D, F, J, K, L, `;`) — Esc/Enter/Quote taps are never affected regardless of Flow Tap settings. It judges purely by timing since the previous keystroke, with no way to distinguish "typing fast" from "reaching to hold a modifier right after typing" — structurally it can be made *less likely* to misfire (shorter term, per-key exemption) but not fixed outright for that pattern.

## Decision log

### ErgoDox EZ / Crymel keymap

- **2024-02 – 2024-03** — ported the then-current Redox layout to ErgoDox EZ; ported Caps Word; moved oneshot-cmd (copy/paste/cut) onto the `/` key's hold; raised `TAPPING_TERM` to 175ms.
- **2026-07-25** — post-rebase fixes; began home-row-mod tap-hold tuning: adopted `PERMISSIVE_HOLD`, `CHORDAL_HOLD`, `FLOW_TAP_TERM`, `SPECULATIVE_HOLD`. Replaced `BOTH_SHIFTS_TURNS_ON_CAPS_WORD` with an F+J combo, specifically to skip the mod-tap hold-resolution delay the shift-based toggle required. Added `_GAMING` (replacing an older "windows mode" concept) as a flat, no-mod-tap, no-layer-tap layer for fast input, modifiers pinned to pinky/thumb as a first draft meant to be tuned by feel. Exempted several same-hand layer-access keys from Chordal Hold's opposite-hand rule (`_MOVE`-quote, `_MOUSE` grv/minus, `_ONESHOTCMD`-slash, umlaut-alt), since those overlays are meant to be chorded same-hand with their own activation key.
- **2026-07-26** — reintroduced a hold layer on `_GAMING`'s Enter (first requested targeting `_MOVE`, corrected to `_SYMB`); this surfaced and led to fixing the layer-numbering bug above, which had also been silently breaking `_MOUSE`/`_SHORTCUTSMAC` in gaming mode. Reverted part of `_GAMING`'s pinky column toward the default layout (quote/move-hold restored right of `;`, three-way rotation of Shift/`/`/quote). Globally swapped every GUI↔CTL keycode/macro (`LGUI_T`↔`LCTL_T`, `LAG`↔`LCA`, `LCTL()`↔`LGUI()`) to remove a macOS-level Cmd/Ctrl software swap that only existed because the layout was originally designed for Windows. Gave `_GAMING`'s Backspace its Ctrl-hold back, swapped Gui/`/` positions on the bottom-right, changed the key right of Shift from Ctrl to Alt. Filled the four unused thumb-cluster slots flanking Enter with numpad operators (`*`/`+` above, `/`/`-` below) on `_QWERTY`, then mirrored onto `_GAMING`.
- **2026-07-28** — diagnosed "hold layers feel slow" (Enter→`_SYMB`, Backspace→Ctrl) as a Permissive-Hold-waits-for-release issue, not a `TAPPING_TERM` issue; fixed via scoped `HOLD_ON_OTHER_KEY_PRESS_PER_KEY` (see above) plus marking Backspace's Chordal Hold position `'*'`. Separately diagnosed "home-row mods never trigger, they turn into letter-repeat" (hit most on S/D held for Option/Cmd right before Backspace) as Flow Tap forcing an early tap decision on a mod-tap it can't see is about to be held. Currently experimenting with a much shorter `FLOW_TAP_TERM` (150ms → 90ms) as a middle ground before deciding between two open options: (a) extend the existing F/J-style Flow Tap exemption to S/D, or (b) drop Flow Tap entirely — since once F/J/S/D are all exempted, its only remaining effect is on A/K/L/`;`, which may not be worth keeping it around for. **No decision made yet** — revisit once the shorter term has been tried in practice.

### Redox wireless keymap

Frozen at the 2024-02 – 2024-03 ErgoDox state (see above): `MACMODE` defaults to Windows, separate `_SHORTCUTS`/`_SHORTCUTSMAC` layers, no Chordal Hold/Flow Tap/Speculative Hold/`HOLD_ON_OTHER_KEY_PRESS`, no `_GAMING`, no GUI/CTL swap, no thumb-cluster numpad operators. Out of date relative to ErgoDox by design (not yet a priority) — don't assume it reflects current preferences.
